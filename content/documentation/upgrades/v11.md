This document is intended to guide you when upgrading from GenHTTP 10.x to GenHTTP 11.

### Target Frameworks

GenHTTP 11 targets `net10.0` and `net11.0`. **.NET 8 and .NET 9 are no longer supported**, so a
project still targeting one of them will not compile until you retarget it.

```xml
<!-- old -->
<TargetFramework>net8.0</TargetFramework>

<!-- new -->
<TargetFramework>net10.0</TargetFramework>
```

The [Ioxide engine](../../server/engines/ioxide/) and its matching test engine are `net11.0`-only,
so stay on .NET 10 if you need to support both.

### API Rework

The dominant change of GenHTTP 11 is a reworked API layer that is better suited to represent
incoming HTTP requests and requires less work by the engine to process the data, resulting
in much higher performance (see the [HTTP Arena results](https://www.http-arena.com/)). Besides the response
content object, the middleware is now allocation-free. For general information about how the new 
API works, see the [request API documentation](../../content/concepts/request-api/).

If your project interacts directly with requests or responses, you will need to adapt it
accordingly. The contracts of high-level handlers such as webservices or static websites did not
change, so they should still compile. The sections below walk through what actually moved.

### Server Setup and Hosting

Hosts are no longer built explicitly - `.Build()` is gone, and you start the server directly with
`.RunAsync()` (or `.StartAsync()` if you want to keep the server instance around).

Console logging is on by default now, so `.Console()` is gone too. If your 10.x code called it -
and almost every sample did - just drop the call.

```csharp
// old
await Host.Create()
          .Handler(app)
          .Console()
          .Defaults()
          .RunAsync();

// new
await Host.Create()
          .Handler(app)
          .Defaults()
          .RunAsync();
```

The old companion mechanism for reacting to every handled request has been folded into the new
[logging capabilities](../../server/logging/) instead; if you need something beyond logging, install
a [custom concern](../../content/concerns/).

A few low-level tuning options for things like the connection backlog and read timeouts were
removed - the engine manages these internally now.

`.Defaults()` also enables automatic HTTPS upgrades and sends a `Strict-Transport-Security` header
now. See [Defaults](../../content/concerns/defaults/) for the full flag table and
[Hardening](../../content/concerns/hardening/) if you need to tune or disable that behavior.

### Request API

Everything you used to read directly off the request moved behind `request.Header`, and the
collections it exposes changed shape - see the [request API documentation](../../content/concepts/request-api/)
for the full picture. The short version:

```csharp
// old
if (request.Method == RequestMethod.Post)
{
    var agent = request["User-Agent"];
    var page  = request.Query["page"];
}

// new
if (request.Header.Method == RequestMethod.Post)
{
    var agent = request.Header.Headers.GetEntry("User-Agent");
    var page  = request.Header.Query.GetEntry("page");
}
```

Request-scoped state also moved: what used to be `request.Properties` is now the
[`Properties`](../../content/concepts/request-api/#properties) bag shared with the server.

By default, the header now stays readable even after you read the body
([`HeaderAccess.Retain`](../../content/concepts/request-api/#header-retention)). In 10.x this was
implicit; in 11.x, handlers that don't need the header afterwards can opt out explicitly to avoid
the allocation.

### Response API

Responses are immutable now. Where you used to mutate a response in place - the normal thing a
concern does - you call [`Rebuild()`](../../content/concepts/request-api/#response-immutability) to
get a fresh builder seeded with the existing status, headers and content:

```csharp
// old
public async ValueTask<IResponse?> HandleAsync(IRequest request)
{
    var response = await Content.HandleAsync(request);
    if (response is not null) response.Headers["X-Powered-By"] = "GenHTTP";
    return response;
}

// new
public async ValueTask<IResponse?> HandleAsync(IRequest request)
{
    var response = await Content.HandleAsync(request);
    response?.Rebuild().Header("X-Powered-By", "GenHTTP");
    return response;
}
```

Content type, encoding and length moved off the response and onto the
[content object](../../content/concepts/response-content/) itself:

```csharp
// old
request.Respond()
       .Content(new StringContent("<h1>Hi</h1>"))
       .Type(ContentType.TextHtml)
       .Build();

// new - the content carries its own type
request.Respond()
       .Content("<h1>Hi</h1>", ContentType.TextHtml)
       .Build();
```

**Custom status codes are no longer possible** - the response builder only accepts the
`ResponseStatus` enum, so if you were relying on something like a raw `299` with a custom reason
phrase, there is no direct replacement.

### The `Flexible*` Types Are Gone

`FlexibleContentType`, `FlexibleRequestMethod` and `FlexibleResponseStatus` have been replaced by
`ContentType`, `RequestMethod` and `ResponseStatus` themselves, which absorbed their capabilities.
Member names are unchanged, so `ContentType.TextHtml` and `RequestMethod.Get` still compile as-is.
What breaks is code that names one of the old wrapper types directly, or calls one of their helper
methods to construct or inspect a value:

```csharp
// old
var type = FlexibleContentType.Get(ContentType.ApplicationJson);
var m    = FlexibleRequestMethod.Get("PROPFIND");

// new
var type = ContentType.ApplicationJson;
var m    = new RequestMethod("PROPFIND");
```

If you're building WebDAV verbs by hand, note that several of the built-in verbs were dropped from
`RequestMethod` - construct them from a string as shown above.

### Routing

The whole routing namespace was replaced by [`IRequestTarget` and `PathSegment`](../../content/concepts/routing/),
including [suffix routing](../../content/concepts/routing/#suffix-routing) for anyone who wrote
custom lookups like `.gz` fallbacks:

```csharp
// old - custom routing handler
var current = request.Target.Current?.Value;
request.Target.Advance();

// new
var current = request.Header.Target.Current?.Decode();
request.Header.Target.Advance();
```

### Custom Handlers and Concerns: `PrepareAsync(IServer)`

Every custom handler's and concern's preparation method now receives the server instance it's
running on. This affects every custom handler and concern in a project, independent of anything
else in this guide:

```csharp
// old
public ValueTask PrepareAsync() => ValueTask.CompletedTask;

// new
public ValueTask PrepareAsync(IServer server) => ValueTask.CompletedTask;
```

A concern just relays the call. Having the server available here is also why this is now where you
resolve [dependency-injected services for setup work](../../content/concepts/dependency-injection/)
rather than in a request.

### File and Resource Serving

Serving files now goes through the new [`GenHTTP.Modules.Files`](../../content/handlers/files/)
package, via `Asset` (single file) and `Assets` (directory/tree):

```csharp
// old
var handler = Download.From(Resource.FromFile("./report.pdf"))
                      .FileName("report.pdf");

var tree = Resources.From(ResourceTree.FromDirectory("./assets"));

// new
using GenHTTP.Modules.Files;

var handler = Asset.From("./report.pdf")
                   .AsDownload("report.pdf");

var tree = Assets.From("./assets");
```

The new module can also
[serve precompressed files](../../content/handlers/files/#precompressed-files) (`file.css.br` next to
`file.css`), which the old handler could not do.

If you implement a custom resource or response content type yourself (for example a database-backed
resource), the [resources](../../content/concepts/resources/) and
[response content](../../content/concepts/response-content/#custom-content-implementations) pages
cover the current contracts in full.

### Webservice and Controller Attributes Take `Method`, Not `RequestMethod`

Because `RequestMethod` is a struct, it can no longer be used as an attribute argument. A new
`Method` enum takes its place - see [Method Definitions](../../content/concepts/definitions/) for
everything else about defining service methods. This touches every webservice and controller class
that specifies a verb:

```csharp
// old
[ResourceMethod(RequestMethod.Post)]
public MyResult Create(MyModel model) => ...;

// new
[ResourceMethod(Method.Post)]
public MyResult Create(MyModel model) => ...;
```

### Reflection Extension Points

If you never wrote a custom parameter injector, formatter or error mapper, or extended `Result<T>`,
you can skip this section - all four contracts changed, see
[Custom Injection](../../content/concepts/definitions/#custom-injection),
[Custom Primitives](../../content/concepts/definitions/#custom-primitives),
[Results](../../content/concepts/definitions/#results) and
[custom error responses](../../content/concerns/error-handling/#custom-error-responses) for the
current shape of each.

One change is worth knowing about even if you never wrote a custom formatter: the built-in
`GuidFormatter` and `DateOnlyFormatter` classes are gone, consolidated into `DateFormatter` and
`FormattableFormatter`. If you referenced either by name, switch to the new types.

### Compression

[Compression](../../content/concerns/compression/) dropped Zstandard support - only Brotli and Gzip
are registered by default now (tracked for a comeback in
[#883](https://github.com/Kaliumhexacyanoferrat/GenHTTP/issues/883) once .NET 11's built-in zstd
support lands). If you implement a [custom compression algorithm](../../content/concerns/compression/#custom-algorithms)
yourself, that contract changed too.

### Websockets

After being declared deprecated in 10.x, the web socket handler based on [Fleck](https://github.com/statianzo/Fleck) 
has been removed in version 11. The closest replacement is the 
[functional flavor](../../content/frameworks/websockets/#functional) of the new websocket module.

If you're writing raw socket-level code, the receive buffer size is no longer configurable (fixed
at 16 KB), and every write method gained a `flush` parameter positioned *before* the cancellation
token - see [Frame Batching](../../content/frameworks/websockets/#frame-batching). If you were
passing the cancellation token positionally, it now silently binds to `flush` instead, so check
those call sites even if they still compile:

```csharp
// old
await connection.WriteAsync(payload, FrameType.Text, true, token);

// new - note the extra flush argument
await connection.WriteAsync(payload, FrameType.Text, true, true, token);
```

### Client Connection and Other Renames

A few smaller, mechanical renames that are easy to miss in a diff:

| 10.x | 11.x |
|---|---|
| `IClientConnection.IPAddress` | [`IClientConnection.Address`](../../content/concepts/request-api/) |
| `LayoutRouter` | [`LayoutHandler`](../../content/handlers/layouting/) |
| `RedirectProvider(string location)` | [`RedirectProvider(Uri location)`](../../content/handlers/redirects/) |
| Dependency injection's `GetServiceProvider(IRequest)` | still there, plus [`GetServiceProvider(IServer)`](../../content/concepts/dependency-injection/) for use during preparation |

A number of public types also became `sealed` - if you were deriving from one of them, you'll need
to change to composition instead.

### ASP.NET Core Adapter

If you're embedding GenHTTP into an existing ASP.NET Core app via the
[adapter](../../server/adapters/#aspnet-core), the companion parameter is gone from the mapping calls
(see [Server Setup and Hosting](#server-setup-and-hosting) above for its replacement), and the
server argument to the run call is now optional:

```csharp
// old
app.Map("/api", handler, companion);
app.Run(handler, server);

// new
app.Map("/api", handler);
app.Run(handler);
```

### Testing

[The testing package](../../testing/) now targets `net10.0`/`net11.0` only, matching the rest of the
framework, and gained an option to
[run the same suite against every engine](../../testing/#testing-against-every-engine), including
Ioxide.

### Packaging

New meta-packages bundle everything for a given engine (`GenHTTP.Full`, `GenHTTP.Full.Kestrel`,
`GenHTTP.Full.Ioxide`), and `GenHTTP.Modules.Files` is the new package you need after the file
serving move above. See [Caching](#caching) below for the packages that were removed rather than
added.

### Body Buffering

In previous versions, the framework buffered the body of an incoming HTTP request into
a memory or file stream, depending on the size advertised by the client. This allowed
users to read the request body multiple times. With version 11, the body is no longer buffered. 
If you need to re-read the body, you can emulate the previous behavior by copying the
incoming body into a memory or temporary file stream.

```csharp
var body = request.GetBody();

if (body is not null)
{
    await using var bodyStream = body.AsStream();

    using var memoryStream = new MemoryStream();

    await bodyStream.CopyToAsync(memoryStream);

    memoryStream.Seek(0, SeekOrigin.Begin);
    
    // use the stream as needed
}
```

Note that reading the body this way is also where the
[header retention](../../content/concepts/request-api/#header-retention) behavior mentioned above
applies - opting out of it will make the header unreadable afterwards.

### Body Arguments

In previous versions, the web service framework did automatically resolve form arguments
from the incoming request body and mapped them to parameters with the matching names. While
this functionality is convenient, it added a performance penalty, even
if no form arguments were used, so this has been extracted into extension methods. 
You can either fetch the arguments from the body or let them inject as a parameter.

```csharp
using GenHTTP.Modules.IO;

var args = await body.AsBodyArgumentsAsync();
```

### Caching

The caching abstraction and all dependent modules have been removed, as the implementations turned
out to be inefficient and slow - the `GenHTTP.Modules.Caching` and `GenHTTP.Modules.ServerCaching`
packages no longer exist, so a reference to either will fail to restore. If you are using caches in
your application, consider using alternatives such as the abstraction layer provided by Microsoft
instead.
